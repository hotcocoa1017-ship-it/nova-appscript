# 2026-09-12 근무조배정관리 회귀 오류

## 증상
- 근무조관리에서 `근무조 불러오기`가 무한 대기처럼 보임.
- 사업장 선택 목록에 운영 사업장 `쏘라노`, `별관`이 정상 노출되지 않음.
- DB의 2026-09-12 근무조/담당동 데이터 자체는 정상이며 최근 저장 요청도 모두 완료 상태였음.

## 원인
1. 2026-09-07~08 전체 DB 전환 과정에서 근무조 클라이언트가 기존 `getShiftManagementData`에서 `getShiftManagementDataDbFirst`로 전환됨. 즉 9/12에 근무조 화면 자체를 직접 수정하지 않았어도, 이미 main에 포함된 DB-first 경로는 이후 전체 Apps Script 배포에서 함께 배포될 수 있음.
2. DB-first 읽기 함수가 DB 조회 성공 후 `SHIFT_MIRROR_PENDING`이 있으면 `mirrorShiftZoneDbStateToSheets_()`를 동기 실행하도록 설계되어 있었음. 이 미러는 Sheet 근무조/담당동 쓰기를 수행하므로 Sheet 지연·잠금·일시 실패가 조회 응답까지 붙잡을 수 있었음. DB-first의 읽기 경로가 레거시 호환 쓰기에 종속된 구조적 회귀임.
3. DB 근무조 RPC는 `nova_users.allowed_sites`를 사업장 선택/접근에 적용했으나, 기존 Apps Script 근무조관리는 운영 사업장 마스터 `getSiteList_()`를 표시하는 구조였음. 이 권한 기준 불일치 때문에 `allowed_sites=['쏘라노']`인 ADMIN/ORDER 계정에서는 `별관`이 누락됨.
4. 기존 DB 전환 검증은 DB-first 라우팅 존재, DB 우선 저장, Sheet 호환 미러 존재 여부만 확인했고, **DB 성공 조회 후 Sheet 쓰기 금지** 및 **기존 사업장 목록 동작의 동등성**을 검증하지 않아 회귀를 차단하지 못함.

## 수정 원칙
- DB 조회가 성공하면 근무조 화면 응답은 즉시 DB 상태를 반환한다. Sheet 미러 pending 여부는 표시 정보일 뿐 읽기 응답을 차단하지 않는다.
- Sheet 호환 미러는 저장 경로의 best-effort 호환 작업으로만 유지한다.
- 근무조관리 ADMIN/ORDER의 사업장 범위는 근무조 모듈에 한해 활성·확정된 사업장 마스터를 기준으로 한다. 다른 모듈의 `allowed_sites` 권한은 변경하지 않는다.
- 한 직원의 A/B/C 복수 근무조 배정은 정상 운영 규칙이며 오류로 간주하거나 차단하지 않는다.

## 영구 회귀 방지 규칙
1. `getShiftManagementDataDbFirst`의 initialized DB-success 분기에서 `mirrorShiftZoneDbStateToSheets_` 호출 금지.
2. 근무조 조회는 DB 확정 상태를 read-only로 즉시 반환해야 함.
3. 근무조 RPC 사업장 목록은 활성·확정 `사업장` 코드 마스터를 기준으로 하며 `allowed_sites`로 목록을 축소하지 않음.
4. 근무조/담당동 저장·bootstrap도 동일한 근무조 전용 사업장 정책을 사용해야 함.
5. 복수 조 배정을 금지하는 전역 중복 검증을 추가하지 않음. 같은 조 내부 중복 제거만 허용.
6. 향후 무관한 기능 배포 전에도 이 규칙을 CI에서 항상 검사하여 전체 프로젝트 배포가 근무조 회귀를 재활성화하지 못하게 함.

## 영향 범위
- 변경 대상: 근무조배정관리 DB 조회의 응답 대기 구조, 근무조/담당동 RPC의 사업장 범위.
- 변경하지 않음: 객실 상태, QM, 룸메이드, 하우스맨 오더, 월별조회, 다른 모듈의 사업장 권한, UI 배치, 근무조 저장 형식, 복수 조 배정 규칙.
